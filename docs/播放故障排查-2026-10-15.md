# 播放全量失败排查 · 2026-10-15

## 结论先说

**不是 API 过期，是我们的「设备身份」被上游封了。**

手机厂商那套签名算法（X-Gorgon / X-Khronos / X-Ladon / X-Argus / X-Medusa）**完好无损**——同一套代码、同一个请求，换成一对新的 `iid` / `device_id`，服务端立刻返回 `Code: 0 请求成功`。

被封的是 vendored 源码里 2026-09 钉死的那一对设备标识（`iid` / `device_id` 两个字段，具体值略）。它在 10-11 还能用，到 10-14 已经被拒绝。

## 现场

电视当时**完全不在线**（100% 丢包、9922/9998/7655 全关、无 ARP 条目），所以「播放全部失败」首先是设备离线；但设备离线恢复后，失败依旧——于是有了下面这场与本机无关上游的复现。

## 证据链（本机复现，无需电视）

新增工具 `tools/probe-upstream.js`，用**与电视服务完全相同的 vm 沙箱**加载 vendored 源码，逐层实测：

| 层 | 结果 |
|---|---|
| `routerData(SITE)` 官网外壳 | ✅ 335ms，`loaderData` 正常 |
| `appSearchPage` App 搜索 | ❌ HTTP 200 但业务失败 |
| `fetchVideoInfo(vid)` 视频模型 | ❌ `video_model failed: 未知异常` |
| `resolveStream(vid)` 签名取流 | ❌ 同上 |

抓住的原始响应体：

```json
{
  "Code": 110001,
  "Message": "未知异常",
  "BaseResp": { "StatusMessage": "unknown error", "StatusCode": 110001 }
}
```

注意 **HTTP 状态是 200**——这是业务码拒绝，不是传输失败。这正是它之前能穿透三层重试的原因：所有重试判定都长在传输错误的形状上（ENOTFOUND / ECONNRESET / 502…），没人认得 `Code 110001`。

## 三分对照实验（定位到「身份」而非「算法」）

| 实验 | 结果 |
|---|---|
| 旧 vid（昨天还能播的那个）| ❌ 110001 未知异常 |
| **全新 vid**（刚从官网搜索拿到，64 集新剧）| ❌ 110001 未知异常 |
| 官网无签名搜索（拿内容用）| ✅ 返回完整剧名/封面/`vid_list` |
| **随机生成的新 iid/device_id** | ✅ **Code=0 请求成功** |
| 再随机一对 | ✅ Code=0 请求成功 |

第一行排除「剧集下架」（旧 vid 与新 vid 表现完全一致，且官网仍有大量内容）；第三行排除「站点挂了」；最后两行排除「签名算法被轮换」——**只剩设备身份被封**。

## 端到端验证

换新身份走完整生产路径（`provider.stream → chunk → decryptPartial`）：

```
series: 首辅娇娘   vid: 7686715217652223038
provider.stream()         1681ms   total=16,975,853
chunk(0,131071) + 解密      16ms   box=ftyp brand=isom
```

`ftyp` + `isom` 是标准 MP4 头，媒体可解密可播。

## 修复（v1.0.0 → v1.0.3）

| 文件 | 改动 |
|---|---|
| `device-id.js`（新增） | 每安装一份设备身份：生成、落盘（`service/.../.device-id.json`）、轮换。**身份只进本机文件，绝不进 git、绝不进 ipk** |
| `provider.js` | `loadUpstream()` 在 `runInContext` 前把当前身份补丁进 vendored 源码（`APP_DEVICE` 由 `DEVICE` 展开，一次覆盖两处） |
| `provider.js` | 新增 `isDeviceRejected()`：识别 `110001` / `未知异常` / `unknown error` |
| `provider.js` | 新增 `reloadUpstream()`：身份轮换后**重新求值** vendored 源码——身份是编译期常量，不重新求值新身份不生效；重新求值同时丢掉旧身份填满的缓存 |
| `provider.js` | `resolveStreamResilient` 遇设备拒绝 → 轮换身份 → 重载 → 重试（上限 3 次，退避 700ms） |
| `provider.js` | `openStream` 每轮与 `signAndPrepare` 改取「当前生效的 api」，避免轮换后还用旧句柄签名 |
| `build.sh` | 打包前把运行时身份文件移出被打包目录（移到 `$TMPDIR`），防止每个安装共用同一身份 |
| `.gitignore` | 忽略 `.device-id.json` |

### 为什么要「重新求值」而不是改个变量

vendored 源码里 `const DEVICE = { iid: '...', device_id: '...' }` 是**求值期常量**。改源码字符串再 `vm.runInContext` 一次，比 fork 上游代码轻得多——而且顺带清空了旧身份的 `streamCache` / `videoInfoCache`（那些签名 URL 对新身份毫无价值）。

## 验证

- 单测 `tools/verify-transient-retry.js`：**22/22 PASS**（新增 6 项：分类器、补丁不误伤漂移的源码块、轮换出的身份格式、**「被拒→轮换→同请求成功」真实案例**、轮换有界、硬错误不误判为封禁）
- 回归：`verify-provider` ALL GREEN、`verify-service` ALL GREEN（`verify-service` 是**真实签名请求**跑通 206 / ftyp / offset / 416 / 404）
- 真机观察：服务在 `verify-service` 运行时确实经历了「被拒 → 轮换 → 成功」，`.device-id.json` 里留着自己写的 `reason: upstream rejected identity (110001)`
- ipk 内容审计：`data.tar` 37 项，**身份文件零泄漏**（期间还抓出并修掉一个真漏洞：第一版把备份文件 `.device-id.json.build-bak` 留在服务目录里，被 ares-package 一起打了进去）

## 复发时怎么办

这个修复是**自愈**的：被封 → 自动换新身份 → 继续播。用户无感。

如果三种新身份全被拒（`DEVICE_ROTATIONS=3` 用尽），说明上游在按更粗的粒度拒绝（IP 段 / UA 指纹 / 签名版本），那才需要重新逆向——届时 `tools/probe-upstream.js` 会直接告诉你是哪一层。

```bash
node tools/probe-upstream.js [vid ...]
```
