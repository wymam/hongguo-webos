## 六、方法与数据质量

### 双通道

1. **资源通道**：脚本 `/tmp/hg-load.sh` 在电视本机每 5 秒采一次
   `/proc/stat`、`/proc/meminfo`、`/proc/net/dev`、`/proc/<pid>/stat`（渲染 23399 / 服务 23418），
   输出 CSV（61 点）。采集脚本经 SSH 上传、`nohup` 运行、数据落盘电视 `/tmp/`，事后取回。
2. **播放通道**：`cdp-inspect.js` + 5 分钟探针（`expr-playback-5min.js`），每 5 秒记录
   `video.currentTime / paused / readyState / buffered / src-tag`（61 点）。

### 已知伪影与剔除

- **`/proc/stat` 首行读数伪影**：12 个采样点出现 ~160,000 jiffies 的整体偏移
  （total 与 idle 同步摆动，疑似某 CPU 核计数在「包含/不包含」间切换）。
  受影响段全部剔除，保留 **48 段** 有效数据。
- **进程级 jiffies 完全干净**（已验证无跳变），进程 CPU 数据不受影响。
- 网络接口实测确认：`eth0` 无流量，真实接口为 **wlan0**；`lo` 承载媒体代理转发。

### 口径说明

- 「占整机 %」= 进程 jiffies 增量 ÷ 全部 4 核 jiffies 增量。
  吃满 1 个核 = 25% 整机。
- 「单核等效 %」= 占整机 % × 4。

## 七、洞察

1. **解码是硬件干的**：starfish 管线仅 ~1.1% 整机（单核 4.4%），
   `<video>` 的解码走硬件单元，CPU 几乎不参与——这解释了为何全链路占用如此低。
2. **切集是唯一成本峰值**：服务进程平时 0.00%，只在换集瞬间冲至 13.75%，
   整机同步到 42.1%（含平台管线重建与 I/O），**5 秒内回落**。
3. **电视 CPU 的主角不是应用**：iconnectivity(3.6%) + systemd(1.6%) + 主框架(0.4%) 等
   系统服务构成 ~13% 的常驻基线，是红果占用的 **15 倍**。
4. **内存曲线健康**：V8 在播放中主动收缩堆（121→78 MB），
   配合系统回收，可用内存反而越播越多——**无泄漏迹象**。
5. **带宽策略有效**：预缓冲让平均需求仅 0.42 Mbps，
   但切集瞬时需求可达 16.7 Mbps（2 MB/s），家庭 Wi-Fi 完全无压力。
